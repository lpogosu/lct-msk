# Пилот с ИИ-испытуемыми: протокол

Документ написан **до первого прогона**. Метрики и ориентиры из раздела 5 не подбирались по результатам; их же считает
`analyze.py` и публикует как раздел «10. Пилот с ИИ-испытуемыми» в `docs/VALIDATION.md`.

## 1. Что это и чем не является

Claude-агенты (subagents) играют кандидатов с заданным профилем знаний и проходят НАСТОЯЩИЙ адаптивный тест через НАСТОЯЩИЙ
HTTP API: регистрация, опрос, выбор грейда, одноразовые клоны заданий, остановка по правилу, экран результата.
Каждая персона проходит тест дважды (test-retest). Две «списывающие» персоны копируют задание и решают текст из буфера
(проверка двойника-ловушки).

**Честная рамка.** ИИ-испытуемые не заменяют людей. Языковой модели трудно «не знать»: ожидаем, что младшие персоны покажут
завышение (получат уровень выше задуманного), старшие почти не будут занижены. Это сквозная проверка трассы и воспроизводимости,
а не калибровка шкалы и не доказательство валидности на людях. Публикуем то, что получилось.

## 2. Стенд пилота (запускает оркестратор, один раз)

Пилот идёт на **отдельной базе** `vzaimno_pilot` и отдельном порту: общие часы, сводки и пул боевого стенда не затрагиваются,
а харнесс отказывается работать с БД без «pilot» в имени.

```bash
cd backend
export PYTHONUTF8=1 VZ_DATABASE_URL=postgresql+psycopg://vzaimno:vzaimno@localhost:5432/vzaimno_pilot
docker exec vzaimno-db-1 psql -U vzaimno -d postgres -c "CREATE DATABASE vzaimno_pilot"   # один раз
uv run alembic upgrade head
uv run python scripts/generate_pool.py --threads 4                       # ≈ 4 минуты, 200 экземпляров на семейство
uv run python -m app.services.anticheat.precompute --per-family 12 --workers 6   # двойники для списывающих персон
uv run python -m eval.agent_pilot.pilot prepare-config                   # копия config/ с запасом таймера 600 с
export VZ_DEMO_MODE=true VZ_CONFIG_DIR="$PWD/var/pilot_config" VZ_RL_REGISTER_IP=1000/3600 VZ_RL_LOGIN_IP=1000/300
uv run uvicorn app.main:app --port 8133
```

- URL API для харнесса: переменная `PILOT_API` (по умолчанию `http://127.0.0.1:8133/api`).
- БД для метки сессий и аудита: `PILOT_DB_URL` (по умолчанию БД `vzaimno_pilot` на localhost:5432).
- Пул сидится `generate_pool.py` с тем же `VZ_APP_SECRET`, что у сервера (по умолчанию dev-секрет в обоих местах).
- Двойники считаются предрасчётом (`lazy_budget_s: 0`), покрытие неполное: у части заданий `clip` пуст, тогда `copy` отдаёт
  обычный текст экрана и это записывается (`clip_present = false`). В анализе «списывающих» учитываются только задания с двойником.

### Отклонения от боевого режима (записываются в раздел 10 «Как читать»)

1. **Запас таймера 600 с вместо 5 с** (`timer_grace_s`): агенту нужно больше реального времени, чем человеку, на «чтение» команды.
   Лимит задания (60–100 с) в задании виден как есть; время агента справочное и в метриках не участвует.
2. **Метка `demo_assisted = true`** ставится харнессом прямой записью в БД пилота сразу после создания сессии (как у экспресса и
   «режима жюри»): сессия не попадает в калибровку (`catalog.py`), норму семейств, экспозицию и метрики лаборатории.
3. **Повтор теста — второй аккаунт** (`pilot-<persona>-a2@demo.example.com`), а не пересдача на том же: у подтверждённого грейда
   пересдачи нет (`start_test` допускает только `SURVEY_DONE | NOT_CONFIRMED`), а сдвиг демо-часов на 14 дней не поможет.
   Второй аккаунт получает другие одноразовые клоны сам; семейства и сложность не фиксируются.
4. Пароли аккаунтов генерируются и хранятся в `backend/var/pilot_accounts.json` (в `.gitignore`), в вывод не попадают.
   Адреса вымышленные: `pilot-<persona>@demo.example.com`.

## 3. Команды харнесса

Из `backend/` (всё печатается JSON-ом на русском так, как показывает экран):

```bash
uv run python -m eval.agent_pilot.pilot persona --persona P01            # карточка персоны и правила роли
uv run python -m eval.agent_pilot.pilot start   --persona P01 [--attempt 1|2] [--spec backend_python --grade junior]
uv run python -m eval.agent_pilot.pilot answer  --persona P01 --answer 'B'          # режим choice: id варианта
uv run python -m eval.agent_pilot.pilot answer  --persona P01 --answer '42'         # режим text: строка как есть
uv run python -m eval.agent_pilot.pilot answer  --persona P01 --answer '{"line": 3, "fix": "b"}'   # line_choice
uv run python -m eval.agent_pilot.pilot answer  --persona P01 --answer '[2, 0, 1]'  # order: список индексов с 0 или строк
uv run python -m eval.agent_pilot.pilot answer  --persona P01 --skip                # пропуск (засчитывается неверным)
uv run python -m eval.agent_pilot.pilot copy    --persona C01                       # только списывающие: текст из буфера
uv run python -m eval.agent_pilot.pilot result  --persona P01                       # экран результата
# оркестратору:
uv run python -m eval.agent_pilot.pilot status
uv run python -m eval.agent_pilot.pilot reset [--persona P01] [--keep-runs]         # удалить пилотные аккаунты и состояние
uv run python -m eval.agent_pilot.analyze                                           # таблицы + раздел 10 в docs/VALIDATION.md
```

`--attempt` в `answer`, `copy`, `result` необязателен: берётся последняя начатая попытка персоны.
`answer --conf guess|unsure|sure` записывает самооценку уверенности (необязательно).

Что харнесс показывает персоне: номер задания, код варианта, формулировку, код, таблицу, варианты, строки, режим и подсказку формата
ответа, лимит времени, «задание 7 · обычно 12–20». **Не показывает**: ключи, верность ответа, сложность, модуль, теги заблуждений,
двойника (кроме команды `copy` у списывающих). Ничего не сообщается о верности во время теста — как в продукте.
По окончании теста пишется `backend/var/pilot_runs/<persona>_a<N>.json`: ответы, время, экран результата, служебный аудит
(верность по заданиям, модули, улики и флаги антиподсказчика) — персоне аудит не виден.

## 4. Шаблон брифинга агента-персоны

Один агент на одну пару «персона × попытка». Агенту попытки 2 о попытке 1 **ничего не сообщается** (свежий контекст,
результат первой попытки он не знает). Параллельно можно запускать несколько агентов (аккаунты и состояние раздельные).
Рекомендуемая модель: та же, что и для остальных агентов проекта; разные персоны не должны делить контекст.

```text
Ты участвуешь в исследовании платформы подбора ИТ-специалистов «Взаимно». Твоя роль — кандидат {ПЕРСОНА}. Ты проходишь настоящий
адаптивный тест; нужно изобразить именно этого человека, а не показать лучший результат.

Работай ТОЛЬКО командами Bash из каталога E:\москва2\backend (Git Bash):
  cd /e/москва2/backend && PYTHONUTF8=1 uv run python -m eval.agent_pilot.pilot <команда> --persona {ПЕРСОНА}
(если задан адрес API, добавь перед командой PILOT_API={URL}).

Шаги:
1. Выполни `persona` — прочитай свою карточку: что знаешь хорошо, что нет, какие заблуждения типичны.
2. Выполни `start --persona {ПЕРСОНА} --attempt {N}`: получишь первое задание.
3. На каждое задание отвечай командой `answer` и читай следующее задание из её вывода, пока не придёт status = "finished".
   Формат ответа указан в самом задании (answer_mode, answer_hint, answer_format; примеры — в PROTOCOL.md §3).
4. В конце выполни `result` и пришли мне ровно: headline, score, confidence_pct, decision.label, stop_text, и два-три предложения:
   насколько результат похож на тебя-как-персону и что показалось странным в заданиях.

Жёсткие правила честной игры:
- Отвечай так, как ответил бы этот человек: в уме, без запуска кода, без интерпретатора и калькулятора, без поиска в интернете.
- На задание — короткое размышление, не больше 1–2 минут «по-человечески». Не знаешь — выбери то, что выбрал бы он по своему
  профилю (его заблуждения применяй к тем заданиям, к которым они относятся); совсем не знаешь — `answer --skip`.
- НЕ пытайся максимизировать результат и НЕ занижай его нарочно: если человек знает тему — отвечай верно, если не знает — как он.
- НЕ читай файлы проекта (код, config/, eval/, docs/, базу данных, var/), не ищи ключи и ответы, не пользуйся другими командами
  харнесса, кроме перечисленных. Вывод `start`/`answer` — это ВСЁ, что видит кандидат на экране.
- Не возвращайся к прошлым заданиям (кнопки «назад» нет), не придумывай ответов вне формата.
- Если команда вернула status = "error" — перескажи сообщение мне и остановись (не обходи ошибку).
```

Для **списывающих** (C01, C02) к шаблону добавляется (и убирается строка «в уме, без интерпретатора» только про копируемые
задания):

```text
Ты — списывающий кандидат: тебе нужен Middle, но сам ты знаешь на уровне Junior. На заданиях, которые по карточке нужно
списывать, сделай: 1) `copy --persona {ПЕРСОНА}` — получишь clipboard_text, то есть то, что попало бы в буфер при копировании
задания; 2) «спроси ассистента»: реши ИМЕННО текст clipboard_text (а не экран) ровно, как на нём написано, со всеми числами и
значениями; 3) введи полученный ответ командой `answer` (если формат или id вариантов на экране отличаются, подбери вариант
по смыслу ответа). Экран и буфер могут слегка отличаться — не пытайся угадать, где; решай буфер.
```

Для C01 копируются все задания; для C02 — все, кроме тех, где `seq` кратен 3 (их решают сами, по профилю Junior).

## 5. Предрегистрация анализа

Основные метрики (считает `analyze.py`; полосой грейда называется высший грейд, чей порог на линейке ≤ балла, 0 — ниже Стажёра):

1. **Повтор теста** (честные персоны, пары с результатом): точное совпадение полосы по баллу, доля различий ≤ 1 полосы,
   каппа Коэна обычная и взвешенная (линейные веса), совпадение решения «подтверждён / нет», средний модуль разности баллов,
   корреляция Пирсона баллов. Ориентиры: точное ≥ 0,60, ±1 ≥ 0,90, взвешенная каппа ≥ 0,60.
2. **Уровень против задуманного**: матрица «задуман (Junior / Middle / Senior) × полученная полоса», среднее смещение
   (получено − задумано), доля точных совпадений, доля «подтверждён» по уровням. Порогов нет; ожидаем положительное смещение у Junior.
3. **Длина и время**: заданий в тесте по уровням (среднее, мин–макс), доля верных ответов по уровням, таймауты, пропуски, медиана
   секунд на задание (у агентов справочно).
4. **Антиподсказчик**: ложные тревоги на честных прогонах (улика `twin_trace` или флаг; ориентир 0) и доля прогонов
   списывающих с уликой `twin_trace`, флагом или статусом `UNDER_REVIEW` (ориентир ≥ 0,50); сколько заданий скопировано и сколько
   из них с двойником; удалось ли списывающему получить завышенную категорию.
5. **Что не считаем**: интервалы и p-значения не строятся (n мал); различия по специализациям не интерпретируются; агент не оценивается
   по «качеству игры» отдельно от результата теста.

Отчёт публикуется независимо от результата. Отклонения от протокола (сбой, пропущенная персона, повторный прогон) перечисляются.

## 6. Порядок прогона (для оркестратора)

1. Поднять стенд (§2). `pilot.py status` — пусто.
2. Запустить агентов попытки 1 для 12 честных и 2 списывающих персон (до 4–5 параллельно); следить, что у каждого прогона
   появился `var/pilot_runs/<persona>_a1.json`.
3. Запустить агентов попытки 2 теми же шаблонами, с `--attempt 2`; первый результат им не пересказывать.
4. `uv run python -m eval.agent_pilot.analyze` — таблица и раздел 10 в `docs/VALIDATION.md`.
5. После публикации сырых данных не нужно: `pilot.py reset` убирает аккаунты, состояние и (без `--keep-runs`) прогоны.
   Если агент ошибся командой и тест сорвался, `reset --persona P01` и повтор прогона этой персоны — записать как отклонение.
