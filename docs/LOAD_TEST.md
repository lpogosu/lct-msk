# Нагрузочный тест

Цель: подтвердить, что стенд на одном сервере (организаторы: ~8 CPU, 32–64 ГБ, без GPU) выдерживает десятки одновременных пользователей
с приемлемым временем основных операций (жёсткого SLA нет), и найти узкие места.

## Метод

- Инструмент: [Locust](https://locust.io) 2.46 (MIT), сценарий `loadtest/locustfile.py`. Запуск против контейнерного стенда через `web` (nginx → backend), то есть через тот же путь, что у браузера.
- Смесь виртуальных пользователей (веса 5 : 2 : 3):
  - **кандидат**: вход → профиль → опрос (4 шага) → запуск теста → ответы на все задания адаптивной сессии с паузами «читает задание» → результат → квалификация; после теста — просмотр (профиль, приглашения, вакансии);
  - **работодатель**: вход → разбор брифа (`parse`) → создание брифа → категории и охват вилки → проверка навыков → сборка подборки → подборка → карточка кандидата → шорт-лист → приглашение; банк кандидатов и сводка, список брифов и воронка приглашений;
  - **гость**: главная и её ассеты, SPA-маршруты, `/api/health`, `/api/fsp/availability`, `/api/docs`.
- Паузы между действиями 1–3 с (кандидат), 2–6 с (работодатель), 1–5 с (гость). У каждого виртуального пользователя свой `X-Forwarded-For` (лимиты входа считаются по IP, а все запросы идут с одной машины): для этого на стенде `VZ_REAL_IP_FROM=172.16.0.0/12`.
- Сбой = 5xx, таймаут или неожиданный 4xx. 409/422/429 на приглашение (лимиты и «активная пара») и 409/422 на ответ в тесте считаются штатными.
- Аккаунты: `backend/scripts/loadtest_accounts.py` создаёт подтверждённых кандидатов `lt0001@loadtest.example` и HR-аккаунты `lthr001@…` при демо-компаниях (лимит запросов подбора считается на аккаунт, поэтому у виртуальных HR свои логины). Для каждого прогона берётся свежая партия кандидатов (`--offset`), потому что повторный тест на том же аккаунте ограничен.
- Длительность прогона 3 минуты, разгон 5–10 пользователей в секунду.

### Как повторить

```bash
docker compose up -d --build && make demo                  # стенд и демо-мир (см. DEPLOY.md)
# для нагрузки с хоста nginx должен верить X-Forwarded-For от хоста (только для теста):
VZ_REAL_IP_FROM=172.16.0.0/12 docker compose up -d web
make loadtest-accounts                                     # аккаунты → loadtest/accounts.json (в .gitignore)
make loadtest USERS=50 RUNTIME=3m                          # отчёт: loadtest/out/u50.html и u50_stats.csv
docker compose exec -T backend python scripts/loadtest_accounts.py --candidates 300 --offset 1000 --out var/loadtest_accounts.json   # свежая партия
```

`make loadtest` запускает Locust через `uvx` (нужен [uv](https://docs.astral.sh/uv/)); без него — `pip install -r loadtest/requirements.txt` и `locust -f loadtest/locustfile.py --headless -u 50 -r 5 -t 3m --host http://localhost`.

## Окружение замеров

Windows 11, Docker Desktop (WSL2), 20 логических ядер, 11 ГБ памяти для Docker; Locust на том же хосте (он тоже потребляет CPU, поэтому цифры слегка занижены относительно отдельной нагрузочной машины). Отдельный проект compose, чистая БД с демо-миром (300 синтетических кандидатов, пул 18 200 экземпляров). Конфигурация стенда: 4 процесса uvicorn (`VZ_WORKERS=4`), пул БД 8+4 на процесс, PostgreSQL `max_connections=200`, `shared_buffers=256MB`.

## Что нашли и исправили

| Прогон | Наблюдение | Причина | Исправление |
|---|---|---|---|
| 1 процесс, 50 польз. | 177 ответов 429 на вход | все запросы шли с одним IP: nginx отдавал бэкенду только адрес прокси | `X-Forwarded-For` теперь идёт от настоящего клиента (`real_ip` в nginx, доверие по `VZ_REAL_IP_FROM`); в тесте у каждого пользователя свой адрес |
| 1 процесс, 50 польз. | 8 ответов 500 на `GET/POST /api/invitations` | **deadlock** в PostgreSQL: `refresh_rows` блокировал ожидающие приглашения `FOR UPDATE` в произвольном порядке, а чтения списков идут параллельно (и с фоновым sweep) | строки блокируются в порядке id; блокировка берётся только если срок/напоминание действительно наступили (пробный прогон без блокировки) — `app/services/contact/store.py` |
| 1 процесс, 50 польз. | 429 `rate_limited` на `/api/needs/*` | 14 виртуальных HR на 6 аккаунтах, лимит 30 запросов/мин на аккаунт | не дефект: у тестовых HR свои аккаунты (40) |
| 1 процесс, 100 польз. | p50 ≈ 1 с даже у `/api/health`, 10 тыс. запросов за 3 мин | один процесс Python упирается в одно ядро (GIL), CPU 120–290 % не помогает | `VZ_WORKERS=4` (uvicorn), пул БД 8+4 на процесс, `max_connections=200`; часы демо синхронизируются между процессами через БД |
| 4 процесса | `GET /api/needs` 440 мс на 90 брифов | N+1: два запроса на каждый бриф (183 запроса) | один запрос брифов + один запрос версий + один группировки закреплённых — `app/services/matching/needs.py`, тест `tests/test_list_needs_batched.py` |

Сводка по этапам (100 пользователей): 1 процесс — p50 1000 мс, p95 2100 мс, p99 3200 мс, 10 тыс. запросов; 4 процесса — p50 74 мс, p95 480 мс, p99 1100 мс, 22 тыс. запросов (рост пропускной способности вдвое при вдвое меньших паузах ожидания клиентов).

## Выводы

- 50 одновременных пользователей: 0 сбоев, медиана 26 мс, p99 400 мс, кроме воронки приглашений (см. ниже). 100 одновременных: 0 сбоев, медиана 74 мс, p95 0,5 с, p99 1,1 с. Запас по CPU на сервере класса 8 CPU примерно двукратный.
- Самые тяжёлые операции: сборка подборки (`versions`, 220–470 мс медиана — Score по всему пулу, его и ожидаем), вход (Argon2, 180–390 мс — сознательная цена защиты паролей), банк и воронка приглашений.
- **Известное узкое место: `GET /api/invitations` (воронка работодателя)**. Список не постраничный, и на каждое приглашение выполняется около 5 запросов (условия, события, раскрытие, проверка исхода, псевдоним). В тесте у одной компании накопились сотни приглашений (каждый виртуальный HR отправляет их без остановки), поэтому 100 пользователей дают p50 1,9 с; у реальной компании в десятки приглашений это ≈ 0,1–0,25 с. Не исправлено: код модуля контакта активно правится в других задачах. Решение: пакетная загрузка связанных таблиц в `to_domain` по списку строк и/или пагинация.
- Лимиты запросов (`RateLimiter`) и буфер `/api/demo/webhook-sink` хранятся в памяти процесса: при `VZ_WORKERS=4` эффективные лимиты до 4 раз мягче. Часы демо (`/api/demo/clock`) синхронизируются через БД раз в секунду.
- Фоновый планировщик защищён рекомендательной блокировкой PostgreSQL, несколько процессов не дублируют задачи.
- Если контейнер упал, `restart: unless-stopped` поднимет его; при падении одного из 4 процессов uvicorn остальные продолжают работать.

## Что не проверено

- Нагрузка с отдельной машины и по сети; сервер класса 8 CPU / 32+ ГБ (замеры на ноутбуке с 20 логическими ядрами и 11 ГБ).
- Более 100 одновременных пользователей и длительные (часы) прогоны; рост БД после тысяч брифов и приглашений.
- Боевая схема с Caddy и HTTPS (`docker-compose.prod.yml`): собран и проверен только конфиг; цепочка Caddy → nginx → backend для клиентского IP (`VZ_REAL_IP_FROM=172.29.80.0/24`) не прогонялась.
- Синхронизация демо-часов между процессами проверена только чтением кода и тестами модуля, живая проверка кнопкой «+1 день» при 4 процессах не выполнена.
